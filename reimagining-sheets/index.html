Reimagining Sheets

28.05.2026

Two weeks ago, as I sat down to start my daily search for an apartment in Berlin (which still feels like a major challenge), I felt the need for a system to track all the applications. My go-to for the past decade was to use Google Sheets, so I started creating the file and the columns, with the goal of manually entering the features of each property. Naturally, only one row in I realized that this was the type of task that an LLM could do so much better, because it's pretty tedious to go to the exposé and manually copy the features of each property into the sheet.

But extraction was only the beginning. I also needed a logging system — a history of actions: sent a request on this date, received an invitation to a visit on that date, sent the application documents the next day. There's no natural way to do that in spreadsheets. Sure, you can create a new sheet and bind them, but it gets messy fast. And spreadsheets are brittle: values get deleted accidentally, formulas break silently. I wanted something robust enough to hold up in court if necessary, with a full history of actions and messages.

What's out there

I looked at the usual options:

Approach Automatic Extraction Activity Logging Enums Setup Complexity
Manual Google Sheets No No (needs separate sheet) Yes (Data Validation) Very low
Google Sheets + in-product AI Partial (formulas, fill, side chat) No Yes (Data Validation) Very low
Notion Partial (AI blocks; mostly manual) Awkward (relations, timeline) Yes (select, status) Low
n8n only Yes Via separate log table Via sheets Medium
OpenClaw + n8n Yes (natural language triggered) Yes (persistent memory + logs) Via sheets High
Claude Cowork / Projects Via chat (unstructured) Conversation only No native schema Low

People are doing this for flat hunts, job applications, and more. But the whole stack involves too many actors and too many data processors. The AI-assisted options are either minimal (a side chat that suggests formulas) or massively wasteful — agentic systems that screenshot your browser, transfer the image, find the button, click, fetch again, screenshot again. Insane amounts of resources so we can save a few minutes.

I went in a different direction.

A declarative, file-based, AI-ready spreadsheet

The whole system is five subsystems, all declarative, so that a human or an AI agent can quickly tweak it:

  • Storage: text files on disk that rebuild a local database as needed. Git tracks every operation, so the history is always there and verifiable.
  • Config: the schema (the shape of the data) plus the flows and prompts. For this use case, I declared that an LLM should grab a property listing and populate the columns I defined.
  • Engine: a minimal Python application that reads the config and manages operations. It watches folders for changes and reacts — producing LLM requests, calling the internal API to update values.
  • Infrastructure: pluggable LLM backends. Local models via Ollama, local agents like Claude Code, or external APIs. Swap one for another without changing anything else.
  • Renderer: a web application to navigate, update values, and trigger flows. Since everything is declarative, new keyboard maps can produce actions — adding a log, viewing a record, fetching details — with a single keystroke.

It is effectively a file-based spreadsheet application with an event-driven pipeline. You get deterministic algorithms for the work that's deterministic, and the power of LLMs for translation, inference, and flagging — each doing what it's actually good at.

How it works

A new property is created from a keyboard shortcut (f, from fetch). This triggers a chain of effects: a log is created, a browser launches to the listing URL, the content is grabbed, an LLM is called to parse it, a new log file is written with the structured data. The web renderer receives a message from the local server and updates the view. The whole flow takes seconds.

The actual chain is: f key → modal → POST /api/ingest → file lands in inbox/ → watchdog fires → preprocessor launches Playwright browser → extracts text/JSON-LD → renders prompt template → calls LLM backend → POSTs structured result to /api/entries → appends to ops.jsonl + updates SQLite → SSE broadcast → web renderer refreshes.

What makes this different

Declarative, not procedural. The schema, the flows, the prompts, the keyboard maps — all declared in config files. No code changes to add a new workflow. Create a new prompt, wire it in the config, it's live.

Event-driven. Every action produces a log entry. Logs rebuild the database. The database is never the source of truth — the files are. Delete the database, rebuild it from logs. Move to a new machine, clone the repo, rebuild.

Multi-dimensional data. The underlying format is JSON, not a flat grid. A record can have nested actions, timestamps, status changes. Export to CSV or XLSX when you need a flat view.

The API protects the system. The LLM doesn't have access to private data. It only parses information that's given to it and updates records through a typed API that enforces the schema. The agent's action space is bounded by the contract, not by trust.

Multiple interfaces almost for free. We got a text-based interface (TUI) with nearly zero extra work. The web renderer is faster for daily use, but the TUI is surprisingly fun and works over SSH.

No automation platform needed. Multiple flows can be created with minimal config. This is not doable with any spreadsheet application, and automation platforms are too cumbersome for something that's fundamentally deterministic.

Tradeoffs

This system requires comfort with the command line. It's not a hosted product you sign into, or an installable application that you download and configure, at least not yet.

On the other hand, Local LLMs struggle with translation — we had to use Claude for certain tasks where accuracy mattered. Scraping is ethically and technically messy, so we avoid it: we solve captchas ourselves when needed and paste URLs manually.

The biggest gap right now is device portability. I can't render this on my phone, so I write notes and dump them later. Git gives me replication across any machine that has it, but the phone is out of bounds for the moment. A future iteration will need a sync layer — being fully decentralized has real limits when half your life happens on a device that can't run a local server easily.

The future is here (almost).

So where are we headed? I believe this is the future of personal computing. It's really personal: some declarations that are easy to understand, some prompts, and we have a working flow that works without any costly subscription, or without giving away our data. It's also built on principles that make it non ephemeral: we can swap the LLM once local models are on par with frontier ones for the current task, and we can continue evolving the renderer and the pipeline to achieve more sophisticated flows, without turning it into a complex, rigid application.

In the end, it's like we are finally realizing that our personal computers can be used for computing!

Notes

  • This prototype is part of moui, a broader project exploring what personal computing looks like when data, interfaces, and infrastructure are separate layers you can swap independently. Sheets is one of four shapes in the workspace — the others handle presentations, blog posts, and websites, all from the same CLI, the same principles.
