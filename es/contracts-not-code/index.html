Contratos, no código

16.04.2026

La mayoría de los sistemas se desvían. Las reglas se infiltran en los command handlers. Un fuzzy matcher escrito para un comando se convierte en un bloque de lógica que nadie más puede usar. Las reglas de negocio y la fontanería se vuelven indistinguibles.

La alternativa es más vieja que el código: declarar lo que existe, dejar que el sistema lea la declaración.

Las cuatro partes

Un núcleo declarativo tiene cuatro partes móviles:

  1. Un registry — YAML o JSON. Lista lo que existe.
  2. Un resolver — empareja la entrada con una entrada del registry.
  3. Un handler — hace el trabajo que la entrada describe.
  4. Un router — canaliza la entrada a través del resolver hacia el handler.

Nada de lógica de negocio en el router. Nada de lógica de emparejamiento en el handler. Cada parte tiene un solo trabajo.

Un registry

Un registry es solo datos. Lista comandos y los patrones que los emparejan.

commands:
  - id: note.create
    patterns: ["new note", "create note", "jot"]
    handler: notes.create
  - id: note.search
    patterns: ["find note", "search notes"]
    handler: notes.search

Agregar un comando significa agregar una entrada. Nada más cambia.

Un resolver

El resolver no sabe qué significan los comandos. Sabe cómo emparejar entrada contra patrones.

def resolve(text: str, registry: list[dict]) -> dict:
    """Return the matching registry entry. Raise if nothing matches."""
    lowered = text.lower()
    for entry in registry:
        for pattern in entry["patterns"]:
            if pattern in lowered:
                return entry
    raise NoMatch(text)

Cámbialo por fuzzy matching, una red neuronal pequeña, un LLM diminuto en el dispositivo. El contrato se mantiene: entrada adentro, entrada del registry afuera.

Un fuzzy matcher no es código dentro de un command handler. Es una capacidad con una interfaz definida que el sistema usa a través de un contrato.

Un handler

El handler no sabe cómo se hizo el emparejamiento. Recibe un contexto y hace el trabajo.

def notes_create(context: dict) -> Result:
    payload = context["payload"]
    note = Note.from_text(payload["text"])
    note.save()
    return Result.ok(note.id)

Los handlers nunca se referencian entre sí. Solo tocan el contexto que reciben.

Un router

El router es la tubería. Tres líneas.

def route(text: str) -> Result:
    entry = resolve(text, registry)
    handler = handlers[entry["handler"]]
    return handler(context_for(text))

Nada de condicionales por nombre de comando. Nada de casos especiales. Si pertenece al router, aplica a cada comando.

Por qué esto se sostiene

La forma del código es lo que lo hace cumplir.

  • No puedes agregar un comando sin agregar una entrada al registry.
  • No puedes cambiar el emparejamiento sin cambiar el resolver.
  • No puedes acoplar handlers porque los handlers solo reciben contexto.

Cada pieza es reemplazable. El router se mantiene estúpido. El emparejamiento vive en el resolver. El trabajo vive en el handler. Contratos en cada costura.

Ese es todo el truco.
