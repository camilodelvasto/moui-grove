Reimaginando las hojas de cálculo

28.05.2026

Hace dos semanas, al sentarme a empezar mi búsqueda diaria de apartamento en Berlín (que todavía se siente como un reto mayor), sentí la necesidad de un sistema para rastrear todas las solicitudes. Mi recurso de la última década era usar Google Sheets, así que empecé a crear el archivo y las columnas, con el objetivo de ingresar manualmente las características de cada propiedad. Naturalmente, con apenas una fila me di cuenta de que este era el tipo de tarea que un LLM podía hacer mucho mejor, porque es bastante tedioso ir al exposé y copiar manualmente las características de cada propiedad en la hoja.

Pero la extracción fue solo el comienzo. También necesitaba un sistema de registro — un historial de acciones: envié una solicitud en esta fecha, recibí una invitación a una visita en esa fecha, envié los documentos de solicitud al día siguiente. No hay una forma natural de hacer eso en hojas de cálculo. Claro, puedes crear una nueva hoja y enlazarlas, pero se vuelve un desorden rápido. Y las hojas de cálculo son frágiles: los valores se borran accidentalmente, las fórmulas se rompen silenciosamente. Quería algo lo suficientemente robusto como para sostenerse en un tribunal si fuera necesario, con un historial completo de acciones y mensajes.

Lo que hay afuera

Miré las opciones habituales:

La gente hace esto para búsqueda de apartamentos, solicitudes de empleo, y más. Pero todo el stack involucra demasiados actores y demasiados procesadores de datos. Las opciones asistidas por IA son o mínimas (un chat lateral que sugiere fórmulas) o masivamente despilfarradoras — sistemas agénticos que capturan pantalla de tu navegador, transfieren la imagen, encuentran el botón, hacen clic, vuelven a buscar, vuelven a capturar. Cantidades demenciales de recursos para que podamos ahorrarnos unos minutos.

Fui en una dirección diferente.

Una hoja de cálculo declarativa, basada en archivos, lista para IA

Todo el sistema son cinco subsistemas, todos declarativos, para que un humano o un agente de IA pueda ajustarlo rápidamente:

  • Almacenamiento: archivos de texto en disco que reconstruyen una base de datos local según sea necesario. Git rastrea cada operación, así que el historial siempre está ahí y es verificable.
  • Configuración: el schema (la forma de los datos) más los flujos y prompts. Para este caso de uso, declaré que un LLM debía tomar un listado de propiedad y poblar las columnas que definí.
  • Motor: una aplicación Python mínima que lee la configuración y gestiona operaciones. Vigila carpetas por cambios y reacciona — produciendo solicitudes al LLM, llamando a la API interna para actualizar valores.
  • Infraestructura: backends de LLM intercambiables. Modelos locales vía Ollama, agentes locales como Claude Code, o APIs externas. Cambia uno por otro sin cambiar nada más.
  • Renderer: una aplicación web para navegar, actualizar valores, y disparar flujos. Como todo es declarativo, nuevos mapas de teclado pueden producir acciones — agregar un log, ver un registro, obtener detalles — con una sola tecla.

Es efectivamente una aplicación de hoja de cálculo basada en archivos con un pipeline dirigido por eventos. Obtienes algoritmos determinísticos para el trabajo que es determinístico, y el poder de los LLMs para traducción, inferencia, y señalamiento — cada uno haciendo aquello en lo que realmente es bueno.

Cómo funciona

Una nueva propiedad se crea desde un atajo de teclado (f, de fetch). Esto dispara una cadena de efectos: se crea un log, un navegador se abre en la URL del listado, el contenido se captura, se llama a un LLM para parsearlo, se escribe un nuevo archivo de log con los datos estructurados. El renderer web recibe un mensaje del servidor local y actualiza la vista. Todo el flujo toma segundos.

The actual chain is: f key → modal → POST /api/ingest → file lands in inbox/ → watchdog fires → preprocessor launches Playwright browser → extracts text/JSON-LD → renders prompt template → calls LLM backend → POSTs structured result to /api/entries → appends to ops.jsonl + updates SQLite → SSE broadcast → web renderer refreshes.

Qué lo hace diferente

Declarativo, no procedural. El schema, los flujos, los prompts, los mapas de teclado — todo declarado en archivos de configuración. Sin cambios de código para agregar un nuevo flujo de trabajo. Crea un nuevo prompt, conéctalo en la configuración, está en vivo.

Dirigido por eventos. Cada acción produce una entrada de log. Los logs reconstruyen la base de datos. La base de datos nunca es la fuente de verdad — los archivos lo son. Borra la base de datos, reconstrúyela desde los logs. Múdate a una nueva máquina, clona el repo, reconstruye.

Datos multidimensionales. El formato subyacente es JSON, no una grilla plana. Un registro puede tener acciones anidadas, timestamps, cambios de estado. Exporta a CSV o XLSX cuando necesites una vista plana.

La API protege el sistema. El LLM no tiene acceso a datos privados. Solo parsea información que se le da y actualiza registros a través de una API tipada que hace cumplir el schema. El espacio de acción del agente está limitado por el contrato, no por la confianza.

Múltiples interfaces casi gratis. Obtuvimos una interfaz de texto (TUI) con casi cero trabajo extra. El renderer web es más rápido para uso diario, pero la TUI es sorprendentemente divertida y funciona por SSH.

Sin plataforma de automatización necesaria. Se pueden crear múltiples flujos con configuración mínima. Esto no es posible con ninguna aplicación de hoja de cálculo, y las plataformas de automatización son demasiado engorrosas para algo que es fundamentalmente determinístico.

Compromisos

Este sistema requiere comodidad con la línea de comandos. No es un producto alojado al que te registras, ni una aplicación instalable que descargas y configuras, al menos no todavía.

Por otro lado, los LLMs locales tienen dificultades con la traducción — tuvimos que usar Claude para ciertas tareas donde la precisión importaba. El scraping es ética y técnicamente complicado, así que lo evitamos: resolvemos captchas nosotros mismos cuando es necesario y pegamos URLs manualmente.

La brecha más grande ahora mismo es la portabilidad de dispositivo. No puedo renderizar esto en mi teléfono, así que escribo notas y las vuelco después. Git me da replicación en cualquier máquina que lo tenga, pero el teléfono está fuera de alcance por el momento. Una iteración futura necesitará una capa de sincronización — ser completamente descentralizado tiene límites reales cuando la mitad de tu vida sucede en un dispositivo que no puede correr un servidor local fácilmente.

El futuro está aquí (casi).

¿Hacia dónde vamos? Creo que este es el futuro de la computación personal. Es realmente personal: algunas declaraciones fáciles de entender, algunos prompts, y tenemos un flujo funcional que funciona sin ninguna suscripción costosa, o sin regalar nuestros datos. También está construido sobre principios que lo hacen no efímero: podemos cambiar el LLM una vez que los modelos locales estén a la par con los de frontera para la tarea actual, y podemos seguir evolucionando el renderer y el pipeline para lograr flujos más sofisticados, sin convertirlo en una aplicación compleja y rígida.

Al final, es como si finalmente nos estuviéramos dando cuenta de que nuestros computadores personales pueden usarse para computar!
